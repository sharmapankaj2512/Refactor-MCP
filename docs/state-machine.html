Refactor-MCP · workflow model

How the refactoring workflow decides what you may write

Four phases, a write-permission table, and a loop between two of Kent Beck's rules of simple design. Every rule below is enforced in phases.py and simple_design.py — this page is a reading of that code, not a wish list.

The premise

Refactoring means changing structure without changing behaviour. You cannot know you preserved behaviour that nothing measures, so production code stays locked until every line and branch in the declared scope is covered. That single rule is why the server exists; everything else follows from it.

Four phases

A phase is a set of write permissions. The server classifies each file as a test, production code, an approved baseline, or something else, then consults one table. Nothing else grants access.

Covered means measured and gapless. A file no test imports has no uncovered lines, so it looks identical to a fully covered file — it is simply absent from the report. The server therefore requires every scope file to appear in the coverage report as well as have no missing lines or branches. An unrelated passing test proves nothing.

Rules 2 and 3 are a loop

Inside refactoring, Kent Beck's rules are a priority order consulted at every decision — not a pipeline you pass through once. Among designs that pass the tests, prefer the one that reveals intention; among those, the one without duplication; among those, the one with fewest elements.

Rules 2 and 3 feed each other. Naming a concept exposes the duplication it was hiding; removing duplication creates an abstraction that needs a name. So they iterate until both are clean at the same moment — and only then does rule 4 apply, because deleting elements while duplication remains hides it rather than removing it.

A rule that changed nothing was not applied

next_rule and complete_refactoring refuse while the current rule has touched no production code in the scope. A counter you can advance for free is not a workflow — and that was a real bug: three next_rule calls with zero edits once reached completion with two rules untouched.

Deletions count. The gate asks changed_paths, not changed lines, because rule 4's whole job is removing code — a pure deletion produces no added lines and would otherwise read as no work at all.

When the code genuinely satisfies a rule already, skip_rule(reason) records why. The reason is echoed in every later reply and in the completion summary, so an honest skip stays possible but becomes visible rather than silent.

What happens on a write

Each gate runs in this order, and the order matters: a file that is both locked and sitting on an uncommitted step reports the lock first, because committing would not unlock it and the other message sends an agent in circles.

  1. resolve_inside(root, path)Refuse anything outside the project root — .., absolute paths and symlink escapes alike.
  2. classify(path)Test, production, approved baseline, or other. A name containing .approved. is a baseline in any language.
  3. exempt?Paths matching REFACTOR_MCP_EXEMPT are written with no test run at all.
  4. open step?A dirty tree with no open step means an earlier step is uncommitted. Repeat edits within one step amend it.
  5. may_write(phase, kind)The permission table. This is where a production write in approval_tests dies.
  6. snapshot, then writeThe previous bytes are kept so the write can be undone.
  7. run the suiteNon-code files return here without running anything.
  8. transition, or revertTests red, a test added during refactoring, or a touched baseline — the snapshot is restored and the reply says what was undone and why.

What the state machine cannot tell you

A clean result means no detectable smells remain, which is not the same as a good design. The detector cannot see misplaced responsibility, a wrong abstraction, or a model that is merely procedural code with better labels. complete_refactoring says so in its own summary.

Every smell detector in this server exists because a human read the refactored code and judged it unfinished while the server reported "satisfied" — feature envy, primitive obsession and shotgun surgery came from one such reading, the anaemic-model detector from the next. The tool narrows what you have to look for. It does not replace looking.
