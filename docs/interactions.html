Refactor-MCP · interaction sequences

Who talks to whom, and in what order

Seven sequences tracing a refactoring from the agent's tool call through the MCP server to the file system, git, and the test runner — including the exchanges where the server says no.

The cast

Four participants appear in every diagram. The server holds no durable state of its own: workflow state lives in memory keyed by project root, and git is the source of truth it recomputes from.

Claude Code The MCP client. Spawns the server as a subprocess and speaks JSON-RPC 2.0 over its stdin/stdout.
refactor-mcp A Python process. Gates every write, runs the suite, keeps phase and rule state in memory per project root.
file system The target project, confined to one root. Writes are snapshotted so they can be undone.
git + pytest Subprocesses. Git answers "what changed and is it committed"; pytest answers "does it still pass, and what is covered".

Sequence 01Startup and handshake

The server is not a daemon. Claude Code launches it per session from .mcp.json and keeps the pipe open; when the session ends, the process ends and all workflow state goes with it.

Sequence 02Declaring a scope, then measuring it

declare_scope only touches the file system to expand folders and classify files. The measurement happens in check_coverage, which is the tool that decides whether production code unlocks at all.

Sequence 03A write that is refused

The central guarantee, as a message exchange: production code is locked until behaviour is pinned. Nothing reaches the file system — no snapshot, no write, no test run.

Sequence 04Pinning behaviour with an approval test

A test write is graded, not just accepted: the suite must pass and the scope must end up fully covered. That is two subprocess runs — the suite, then coverage — because passing is not the same as covering.

Sequence 05A refactoring that breaks behaviour

Rule 1 — passes all the tests — is enforced here, by undoing the edit rather than warning about it. The snapshot taken before the write is what makes that possible.

Why the baseline is locked while refactoring. Rewriting an approved file is the one way to make a changed behaviour look green. The server refuses it outright and says where a real behaviour change belongs — a test-driven cycle, not this one.

Sequence 06Working a rule, and the loop reopening

After an accepted write the server re-measures the scope and compares target counts before and after. That is how it notices both the loop feeding forward and an edit that bought a lower-ranked rule by spending a higher one.

Measured, not asserted. In one Gilded Rose run the step that cleared the last naming target is the same step where duplication first appeared — intention 1→0, duplication 0→1. The loop is in the data, not just the docs.

Sequence 07Completing, and committing through RACN

Completion runs three checks and then discards the session. Commits are a separate server's job: refactor-mcp refuses the next step's edits until the previous one is committed, but it never commits for you.

Every subprocess the server runs

No network calls, no daemons. The server shells out for exactly two kinds of answer: what git knows about the tree, and what the test runner reports.

Two details that caused real bugs

PYTHONDONTWRITEBYTECODE=1 is set on every run. Python validates .pyc files on whole-second mtime and size, so cached bytecode can run stale code after a quick same-size edit or a revert — exactly the pattern this server produces.

The project's own .venv interpreter is preferred over the server's, so the suite runs with the dependencies the project actually declares rather than the server's.

Where the state lives

Workflow state is a dictionary keyed by resolved project root — phase, active rule, scope, the base commits, and which rules were skipped with a reason. It is never written to disk.

That makes git the durable truth and check_coverage the resync: call it after a server restart or when the repository changed underneath, and the phase is recomputed from the tests. The cost is real, though — a restart mid-refactoring loses the rule position, so the work gate sees "no production change since rule_base" and asks for work that was already done.
